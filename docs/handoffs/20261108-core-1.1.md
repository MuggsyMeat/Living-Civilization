## 1. Gameplay handoff: `hasChunk` expects chunk coordinates

The spawn command is unchanged. Gameplay owns it.

`LivingCivilizationCommands.spawnHuman` currently calls:

```java
level.hasChunk(spawnPos.getX(), spawnPos.getZ())
```

`spawnPos` is a `BlockPos`. `getX()` and `getZ()` are block coordinates. On Minecraft Java **26.3**, `hasChunk(int, int)` consumes those integers as **chunk** coordinates. Passing block coordinates checks a different chunk, often one that is not loaded, so a loaded spawn position can be rejected. Near the origin the two spaces can accidentally overlap; that is not evidence the call is correct.

### Recommended loaded-only call

Use the block-position API, which converts and does not add a chunk ticket:

```java
level.hasChunkAt(spawnPos)
```

`Level.isLoaded(BlockPos)` is the bounds-aware alternative. It also converts block coordinates and does not add a ticket. It returns false when `isInValidBounds` fails (build height, then `ChunkPos.isValid` on the converted chunk coordinates). The spawn command already checks the world border separately.

Do not pass block X/Z to `hasChunk(int, int)`.

`Level.getBlockState(BlockPos)` is not a loaded-only read. After the bounds check it calls `getChunk(chunkX, chunkZ)`, and that path uses the create flag `true`. On `ServerChunkCache`, create `true` calls `addTicket` (`TicketType.UNKNOWN`) before generation. Gameplay should keep a correct loaded check before any `getBlockState` / block edit, and should not use `getBlockState` as the loaded test. This PR does not change that call.

`ServerLevel` extends `Level` and does not declare `hasChunk`. `Level` implements `LevelAccessor`. `LevelAccessor` extends `CommonLevelAccessor`, which extends `LevelReader`.

- `LevelReader.hasChunk(int, int)` — abstract. Callers that already hold chunk coordinates use this. `hasChunksAt(int, int, int, int)` converts block coordinates with `SectionPos.blockToSectionCoord` and then calls `hasChunk`.
- `LevelReader.hasChunkAt(int, int)` — default. `blockToSectionCoord` on each argument, then `hasChunk(chunkX, chunkZ)`. These arguments are block coordinates.
- `LevelReader.hasChunkAt(BlockPos)` — default. Reads block X/Z and calls `hasChunkAt(int, int)`.
- `LevelAccessor.hasChunk(int, int)` — default. Forwards both integers unchanged to `ChunkSource.hasChunk(int, int)`. No shift.
- `Level.isLoaded(BlockPos)` — `isInValidBounds`, then `SectionPos.blockToSectionCoord` on X and Z, then `ChunkSource.hasChunk`. No ticket.
- `ChunkSource.hasChunk(int, int)` — `getChunk(x, z, ChunkStatus.FULL, false)`. The boolean is the create flag and is false.
- `ServerChunkCache.hasChunk(int, int)` — overrides the above. `new ChunkPos(x, z)`, `getVisibleChunkIfPresent`, then `!chunkAbsent(holder, ChunkLevel.byStatus(ChunkStatus.FULL))`. `chunkAbsent` is true when the holder is null or `getTicketLevel() > fullLevel`. No `addTicket` call.
- `ChunkPos(int, int)` — stores the arguments in record fields `x` and `z`. `getMinBlockX()` is `SectionPos.sectionToBlockCoord(x)`.
- `SectionPos.SECTION_BITS = 4`, `SECTION_SIZE = 16`. `blockToSectionCoord(int)` is arithmetic `>> 4`. `sectionToBlockCoord(int)` is `<< 4`.
- `Level.getBlockState(BlockPos)` — void air when `!isInValidBounds`; otherwise `getChunk(section(x), section(z))`.
- `Level.getChunk(int, int)` — calls `getChunk(x, z, ChunkStatus.FULL)`.
- `LevelReader.getChunk(int, int, ChunkStatus)` — default, create flag `true` (`iconst_1`).
- `ServerChunkCache.getChunkFutureMainThread(..., boolean create)` — when `create` is true, `addTicket(new Ticket(TicketType.UNKNOWN, level), chunkPos)`.

Illustration from that shift, not from a running world: block `(100, y, 200)` is chunk `(6, 12)`. `hasChunk(100, 200)` asks for chunk `(100, 200)`, whose minimum block corner is `(1600, 3200)`.

## 2. Runtime dependency ranges

Selected pins were not changed: `gradle.properties` still has Minecraft `26.3`, Loader `0.20.1`, Loom `1.19.4`, Fabric API `0.165.2+26.3`. The wrapper URL is still Gradle `9.8.2`. Compile target remains Java 25. Plugin id remains non-remapping `net.fabricmc.fabric-loom`.

`fabric.mod.json` `depends` was tightened to the versions this stack actually selects. Broader ranges were claiming compatibility that this project has not verified.

| Key | Previous | Now | Why |
|---|---|---|---|
| `fabricloader` | `>=0.20.1` | `0.20.1` | Loader 0.20.1 parses a bare version as equality. `>=0.20.1` also matched `0.20.2` and unrelated higher versions in the predicate check below. |
| `minecraft` | `~26.3` | `26.3` | `~` is `SAME_TO_NEXT_MINOR`. Measured interval was `[26.3,26.4)`, so `26.3.1` matched. Only release `26.3` is selected. |
| `java` | `>=25` | `25` | Loader registers builtin mod `java` as `System.getProperty("java.specification.version")` (`ModDiscoverer`). Temurin 25.0.5 reports specification version `25` and `java.version` `25.0.5`. Equality `25` matches the specification version and rejects `26`. `>=25` matched `26`. Equality `25` does **not** match the string `25.0.5`; that string is not what Loader compares. |
| `fabric-api` | `*` | `0.165.2+26.3` | `*` matched every version tested. The published API jar `fabric-api-0.165.2+26.3.jar` declares `"version": "0.165.2+26.3"`. |

Predicate check, executed on Temurin 25.0.5 with `fabric-loader-0.20.1.jar` (`VersionPredicate.parse` / `Version.parse`):

- `26.3` matches `26.3` only among `26.3`, `26.3.1`, `26.4`, `26.3-rc-1`.
- `~26.3` matches `26.3` and `26.3.1`, not `26.4` or `26.3-rc-1`.
- `0.20.1` matches `0.20.1`, not `0.20.2` or `0.19.5`.
- `25` matches `25`, not `25.0.5` or `26`.
- `0.165.2+26.3` matches `0.165.2+26.3`, and also `0.165.2` and `0.165.2+26.4`. It does not match `0.165.3+26.3`.
- Maven metadata `https://maven.fabricmc.net/net/fabricmc/fabric-api/fabric-api/maven-metadata.xml` publishes both `0.165.2+26.3` and `0.165.2+26.4`. Loader 0.20.1 `SemanticVersionImpl.compareTo` ignores the `+` build key, so the depends string records the selected artifact but does not reject the `+26.4` build. The Gradle pin `fabric_api_version=0.165.2+26.3` still selects the 26.3 artifact at build time. No stronger predicate exists in this Loader. This is not a claim that runtime loading rejects `0.165.2+26.4`.

Fabric API's own metadata uses wider ranges (`fabricloader >=0.19.3`, `java >=25`, `minecraft ~26.3-`). Those are Fabric's claims, not evidence that this mod was tested on that range, so they were not copied.

The built jar's `fabric.mod.json` contains the tightened depends and version `0.1.0`. `verifyModJar` still accepts it because `depends.minecraft` contains `26.3`.
