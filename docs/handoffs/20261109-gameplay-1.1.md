## What changed

`LivingCivilizationCommands.spawnHuman` no longer calls `hasChunk(int, int)` with block coordinates.

Before any `getBlockState`, `isFaceSturdy`, `getCollisionShape`, `noCollision`, or `addFreshEntity` the candidate must pass:

1. The existing world-border test on the spawn block.
2. `Level.isInValidBounds` on the floor, body, and head. On 26.3 that is build height plus `ChunkPos.isValid` of the section coordinates.
3. `Level.isLoaded` on every column in the collision cursor, sampled at the spawn block's Y.

The cursor is the entity bounding box after `setPos`, expanded the way `BlockCollisions` does: `floor(edge - 1.0E-7) - 1` through `floor(edge + 1.0E-7) + 1`. Chunks are full-height columns. For this 0.6-wide body the horizontal cursor is three blocks on a side, so checking each of those columns covers every overlapped chunk. `isLoaded` is bounds-aware and calls `ChunkSource.hasChunk` after `blockToSectionCoord` (`>> 4`). It does not add a ticket. The `LevelReader.hasChunk` / `hasChunksAt` overloads are deprecated on this jar, so they are not called.

Search limits, gamemaster permission, player-only execution, one successful `addFreshEntity`, and the failure message with no block edits are unchanged. An entity object may be constructed to read its box; it is not inserted unless the footprint is loaded and the later checks pass.

## 26.3 evidence used

Official server jar, not Yarn. Outer SHA-1 `33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`. Inner `META-INF/versions/26.3/server-26.3.jar` SHA-256 `a362163eec5d1612d520772bc16e5b39c09e3b234fdc045f56bf544284ee8ae6`.

Re-checked with `javap -c -p` on that inner jar for the methods this change calls or avoids:

- `SectionPos.blockToSectionCoord(int)` is `ishr` by 4.
- `Level.isInValidBounds(BlockPos)` is `isInsideBuildHeight` and `ChunkPos.isValid` on section coordinates.
- `Level.getBlockState` returns void air when bounds fail. On valid bounds it calls `getChunk`, and `ServerChunkCache.getChunkFutureMainThread` calls `addTicket(TicketType.UNKNOWN)` whenever the create flag is true.
- `CollisionGetter.noCollision` reaches `BlockCollisions`, which calls `getChunkForCollisions` (`getChunk` with create `false`). A null chunk getter is skipped, so an unloaded chunk is treated as empty.
- `BlockCollisions` builds its cursor with `1.0E-7` and then ±1 block. For the 0.6×1.8 human centered on a block, that horizontal span is the spawn column plus one block, which crosses a chunk edge when the column sits on a chunk boundary.
- `EntityDimensions.makeBoundingBox` is center ± width/2 and feet through feet+height. `setPos` installs that box.
- `Level.isLoaded(BlockPos)` is not deprecated. It returns false when `isInValidBounds` fails, otherwise `ChunkSource.hasChunk` on section coordinates. `ServerChunkCache.hasChunk` does not call `addTicket`.
- `LevelReader.hasChunk`, `hasChunkAt`, and `hasChunksAt` are deprecated on this jar. `hasChunksAt(int, int, int, int)` still takes min block X, min block Z, max block X, max block Z and only calls `hasChunk`, but the command uses `isLoaded` instead.

## Proposed QA regression cases

Not run here:

1. Positive chunk boundary. Player in a loaded chunk whose block X or Z is the last block of the chunk (`local & 15 == 15`), including a non-origin chunk such as chunk `(6, 12)` / block `(100, *, 200)`. A safe floor in the next loaded chunk spawns one human. The old `hasChunk(blockX, blockZ)` call rejects that loaded column.
2. Negative chunk boundary. Same case for negative block coordinates (`local` 0 of a negative chunk, so the cursor's −1 block crosses into the more-negative chunk). One spawn when that neighbor chunk is loaded and the column is safe; zero when it is not.
3. Unloaded adjacent footprint. Spawn column loaded, but the chunk touched by the ±1 cursor is not loaded. Expect zero entities and no new chunk ticket. `noCollision` alone would skip that chunk and can report the space empty.
4. Failure accounting. Out-of-bounds floor, body, or head, or any unloaded cursor chunk: command returns 0, the failure text is unchanged, no block edits, and `addFreshEntity` is not called.
5. One success. The first safe loaded column inserts one entity and returns. Later candidates are not inserted.

## Remaining issues

- Shape callbacks can read farther than this cursor. `isFaceSturdy` and `getCollisionShape` receive the `Level`. A block implementation that asks for a neighbor beyond the ±1 cursor can still call `getBlockState` and add a ticket. Not chased in this change.
- A successful read still uses `getBlockState`. On 26.3 that path adds `TicketType.UNKNOWN` even when the chunk is already present. The guard stops that call when the footprint is unloaded. It does not make a successful read ticket-free.
- No player-protection registry exists in this mod. Unloaded chunks are refused and blocks are not edited. A protection claim cannot be consulted yet.
- LC-SPC / LC-ENG requirement text was not in the repo, so this note cannot quote it.
- In-game spawn, dedicated server, and Windows play were not run.
